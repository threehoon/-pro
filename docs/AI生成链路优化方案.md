# AI 生成链路优化方案（速度 · token · 超时）

> 覆盖面试总结、复合评价、面试题、简历筛选、岗位画像五类生成。数据来自 `server/data/hireloop.db` 的 `ai_runs` 实测与一次对照探针调用（2026-11-27）。
> 本文是待评审方案，评审通过后按 P0 → P1 → P2 拆成独立 PR。
>
> **状态（2026-11-27）**：P0 与 P1 已实现并实测，见 §10；P2-1 一并做了，P2-2/P2-3 未做。

## 0. 结论速览

一句话：**慢和贵都不是因为写得长，而是因为模型在「想」，而我们既没关掉思考、也没设输出上限。**

- 五类任务里，输出 token 的 **60%–92% 是思考内容**（`reasoning_tokens`），我们从不展示、也不存储。
- 四类任务（总结/复合/面试题/筛选）从未下发 `thinking` 开关，一律吃服务商默认值（= 开启）。
- 四类任务没有 `max_tokens`，唯一的闸门是 45s 超时——**超时既拿不到结果，又照付 token**。
- 关掉思考的对照实测：同一份转写，输出 421 token / 3.1s 出完整合法 JSON；不关则 800 token 全是思考、6.0s 一个字没写。

预期收益（估算，见 §3、§6）：总结耗时 **37.6s → 约 8s**，全流程 token **约 6.8 万 → 约 2 万**，超时失败 → 0。

## 1. 体检：钱和时间花在哪

### 1.1 每类任务的实测开销（真实库均值）

| 任务 | 输入 token | 输出 token | 平均耗时 | 存下来的正文（估） | **思考占比** |
| --- | --- | --- | --- | --- | --- |
| 面试总结 summary | 4 912 | 7 940 | 37.6s | ≈1 045 token | **87%** |
| 复合评价 composite | 5 521 | 7 489 | 35.2s | ≈632 token | **92%** |
| 简历筛选 screening | 5 875 | 3 359 | 17.4s | ≈377 token | **89%** |
| 面试题 questions | 4 052 | 2 036 | 13.4s | ≈491 token | **76%** |
| 岗位画像 profile | 1 702 | 2 670 | 16.4s | ≈1 056 token | **60%** |

正文 token 由「数据库里实际存下的 JSON 字符数 ÷ 2.2」折算（2.2 字符/token 来自实测的关思考样本）。

### 1.2 耗时几乎完全等于输出 token ÷ 212

各类任务的稳定吞吐为 150–220 token/s，与输入长度基本无关：

| 任务 | 输出 token | 耗时 | 吞吐 |
| --- | --- | --- | --- |
| summary | 7 793 | 35.8s | 218 token/s |
| summary | 8 827 | 42.3s | 209 token/s |
| summary | 7 263 | 36.5s | 199 token/s |
| summary | 7 876 | 35.7s | 221 token/s |

结论：**想缩短耗时，只有两条路——少让它输出（尤其少让它思考），或者不让用户干等（流式/预生成）。** 连接开销（已优化的 ~85ms）在这个量级上占 0.2%，没有进一步空间。

### 1.3 探针证据（一次对照调用，约 2k 输入 / 2.8k 输出）

同一条总结提示词、同一份 300 字转写，只改思考开关：

| 请求 | 输出 token | 其中思考 | 正文 | 耗时 | finish |
| --- | --- | --- | --- | --- | --- |
| 默认（不传 `thinking`） | 800（打满） | **800** | 0 字 | 6.0s | `length` |
| `thinking: {type:'disabled'}` | 421 | 0 | 931 字合法 JSON | **3.1s** | `stop` |
| `reasoning_effort: 'minimal'` | 800（打满） | **800** | 0 字 | 5.8s | `length` |

说明：该服务商默认开启思考，`thinking` 参数有效，`reasoning_effort` 被忽略。

### 1.4 为什么会变成这样（根因）

1. **思考开关只对画像生效**：`server/src/services/recruitment-ai.ts:218` 的 `options` 只在 `kind === 'profile'` 时构造，其余四类传 `undefined` → 不下发 `thinking` → 用默认值（开）。
2. **开关还绑死了官方域名**：`server/src/integrations/llm.ts:252` 的 `useDeepSeekThinking` 要求 URL 命中 `^https://api.deepseek.com`。当前配置确实是官方地址，所以画像能用；但换个兼容服务商就会静默失效，属于隐藏地雷。
3. **没有输出预算**：只有 `profile` 传 `maxTokens: 5200`，其余四类靠 `LLM_TIMEOUT_MS = 45_000`（`server/src/integrations/llm.ts:15`）兜底。按 212 token/s 算，45s ≈ 9 500 token 就是硬顶——总结常态 7 800–8 800，已在悬崖边，历史出现过 `timeout`。
4. **失败即报废**：`server/src/services/recruitment-ai.ts:231` 的自动重试只针对 `profile`（且只对 `empty_response`/`malformed_json`/`invalid_profile_structure`）。其余四类一次超时/截断就直接 `failed`，**用户白等 45 秒、token 照付、还得手动重试**。
5. **输入冗余**：总结输入 6 300–7 400 token，其中转写只有 300–400 字，大头是整份岗位画像（含四组指标 × 3–6 标签 × 五档行为描述）、整份简历、上一轮总结全文。总结正文只用到标签名和档位，用不到五档标准描述。
6. **前缀缓存基本命不中**：`server/src/services/recruitment-ai.ts:544` 的输入对象把每次都变的 `transcript` 放在第一个字段，稳定的大段画像/简历排在后面；服务商的上下文缓存按前缀匹配，第一个字节就不同 → 全量按未命中计价。而且我们**没有记录** `prompt_cache_hit_tokens`，命没命中完全看不见。

## 3. P0：先做这三件（收益最大、改动可控）

### P0-1 思考开关按任务下发，四类默认关闭

- **做法**：`llm.ts` 的 `RequestOptions` 增加 `reasoning?: 'off' | 'on'`；是否下发 `thinking` 不再依赖官方域名，改为「配置项声明该服务商支持 + 该任务策略」。`recruitment-ai.ts` 为每个 `kind` 定义策略：`summary`/`composite`/`questions`/`screening` 默认 `off`；`profile` 维持现状（首次 off、重试 on）。
- **为什么**：思考占了 76%–92% 的输出 token，是耗时和费用的唯一主因；探针已证明关闭后仍能产出合法结构。
- **收益**：输出 token ≈ −80%，耗时 ≈ −75%（37.6s → 约 8s）。
- **风险**：判断质量可能下降（尤其 `evidence: strong/weak` 的取舍、是否漏掉 `unanswered`）。
- **控制**：保留开关并在设置页可切；`PROMPT_VERSIONS` 递增，`ai_runs.prompt_version` 记录版本，可按键回滚对比。
- **验证**：`npm run bench -- --thinking off` 与 `--thinking on` 同输入对比；抽检 10 份总结对比引用与指标。
- **归属**：调度与传输（框架侧）；质量口径与抽检（AI 质量侧）。

### P0-2 输出预算：给四类任务设 max_tokens

- **做法**：`summary 2 200`、`composite 1 800`、`screening 1 800`、`questions 1 200`、`profile 保持 5 200`（均为关思考后的余量，约为正文量 ×1.4）。
- **为什么**：现在没有预算，45s 超时是唯一闸门；超时/截断等于「付了钱、没结果、还要重来」。
- **收益**：把「无限等待」变成「最多 N 秒一定有结论」；配合 P0-1 后，单次最坏耗时降到 10s 量级。
- **风险**：极端长面试可能被截断（`finish_reason=length` → `truncated_response`）。
- **控制**：截断时不静默失败——走 P0-3 的降级重试（放宽预算一次），仍失败则明确提示「本次内容较长，已改用精简总结」。
- **验证**：用库里最长转写 + 一组合成长转写（1 2000 字上限）各跑一遍，确认不截断。

### P0-3 分层超时 + 一次降级重试

- **做法**：按任务设超时——`summary`/`composite` 30s、`screening`/`questions` 25s、`profile` 45s；超时或 `truncated_response` 且**尚未收到响应**时，用更低预算（`max_tokens` × 0.6、`reasoning: off`）重试一次；已收到响应一律不重放（延续现有避免重复计费的原则）。
- **为什么**：现状是一次超时全废；画像有重试兜底，其余四类没有。
- **收益**：超时失败从「必然报废」变成「大概率仍出结果」；最坏链路时间可控。
- **风险**：降级结果可能偏短，需要前端标注「精简模式」。
- **验证**：注入一个延迟响应（测试里替换 `llmTransport`）确认重试发生且不重复计费。

### P0-4 把思考与缓存 token 记进库（可观测）

- **做法**：`decodeLlmResponse` 解析 `completion_tokens_details.reasoning_tokens` 与 `prompt_cache_hit_tokens`；`ai_runs` 用 `ensureColumn` 增量加 `reasoning_tokens`、`cached_tokens` 两列。
- **为什么**：本次能定位问题靠手工探针，正常路径完全看不出「钱花在哪」。没有这项，后面所有优化都无法验收。
- **收益**：设置页/运维可直接看每类任务的正文与思考占比、缓存命中率。
- **归属**：框架侧（与 P0-1 同一 PR 更省事）。

## 4. P1：输入侧与缓存（省输入费用、再快 1–2 秒）

### P1-1 总结的输入瘦身

- **做法**：`summaryInput`（`recruitment-ai.ts:544`）里把整份画像换成「指标标签清单 + 红线 + 硬性条件」；`previous` 只保留 `headline` 与 `concerns` 的 `point`，不再塞整份上一轮总结；`plan` 只传问题文本。
- **为什么**：输入 6 300–7 400 token 中大段是画像五档描述和上一轮全文，总结正文根本用不到。
- **收益**：输入降 50%–60%，prefill 少 1–2s，输入费用减半。
- **风险**：`indicators_checked` 的 `indicator`/`label` 必须与画像标签严格对齐（`validateSummary` 会按画像校验），所以**只删描述文本、保留标签集合**。
- **验证**：`server/test/recruitment-ai.test.ts` 增加「画像描述被裁剪但标签校验仍通过」用例；抽检 10 份总结的标签覆盖数不下降。

### P1-2 输入字段重排以命中前缀缓存

- **做法**：输入对象顺序改为 `profile → resume → plan → previous → transcript`（稳定内容在前、变化内容在后）。
- **为什么**：上下文缓存按最长公共前缀匹配；现在 `transcript` 排第一，每次都从头不同。
- **收益**：同一岗位/同一候选人的重复生成（含重试、复合评价复用）输入按命中部分低价计费。
- **风险**：改结构会让 `input_hash` 变化，**24h 缓存一次性失效**（一次性代价，可接受，需在 PR 说明）。
- **验证**：连续两次生成后查 `cached_tokens > 0`；`ai_runs` 输入 token 明显下降。

### P1-3 链路依赖（已验证，无需改动）

复合评价在每次总结保存后被触发，但 `composite_status` 与 `queueComposite` 的早退保护已经生效——真实库里每个投递的复合评价只跑了 1 次，没有重复烧钱。**保持现状**，仅在文档中说明。

## 5. P2：感知速度与长期保护

- **P2-1 生成中显示进度**：现在只有一句静态文案（`web/src/components/workflow/InterviewDrawer.tsx:149`「正在从逐字稿提取证据…」）。改为「已用时 6 秒 · 通常 8–12 秒」，让等待可预期。总时长不变，等待感明显下降。
- **P2-2 批量场景限流与预算**：批量导入简历会一次性排队几十份筛选。加每日/每批 token 上限与可见的进度，避免「一键烧掉几十块」。
- **P2-3 分任务选模型**（可选）：轻任务用小模型、总结保留当前模型。需要设置页支持每任务指定模型，成本中等。
- **P2-4 流式输出**（**不建议现在做**）：能 1–2 秒看到第一段，但需要前后端改造，且与 `response_format: json_object` 冲突（半截 JSON 要增量解析）。在 P0-1 把 37s 降到 8s 之后，收益不足以支撑这个改造成本。

## 6. 还有哪些方法，以及为什么暂时不做

| 方法 | 预期收益 | 判断 | 理由 |
| --- | --- | --- | --- |
| 换成自带非思考的模型跑轻任务 | 与关思考接近 | 可选 | 若 `thinking:disabled` 已等效，额外收益有限，却要多维护一套模型配置 |
| 两段式生成（先结论、后细节懒加载） | 感知快 | 暂不做 | 总 token 增加，且要拆接口与前端两段渲染 |
| 把「面试题 + 总结」合并成一次调用 | 省一次输入（约 5k） | 暂不做 | 两类任务触发时机不同，且失败会互相拖累 |
| 延长缓存窗口（24h → 7 天，内容不变即复用） | 省重复生成 | 可做，成本低 | 现有 `input_hash` 已是内容指纹，24h 只是保险；建议改成「内容不变永久复用 + 手动强制刷新」 |
| 缩小画像本身（生成时就别写那么长） | 连带省下所有下游输入 | 交给质量侧 | 属提示词与质量标准，需与画像评审口径一起改 |
| 提高并发（现在 `running < 3`） | 单用户无收益 | 不做 | 单用户串行链路不受并发限制；批量场景用 P2-2 的限流更合适 |
