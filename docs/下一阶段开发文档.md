## 0. 一句话

**每个候选人永远只有一个主按钮**；每个需要拍板的节点，AI 已经把结论摆好，人只点"下一步"或"归档"。

## 1. 相对上一版改了什么

| # | 变化 | 原因 |
|---|---|---|
| 1 | **新增「岗位画像」**（建岗后 AI 自动生成，人确认一次） | 你说的流程第一步就是出画像；筛选必须对着画像，不是对着 JD 原文 |
| 2 | **筛选恢复评分**，但模型只判档、不算分 | 你要求"筛选评分"；让模型直接报 78 分是假的，让模型判"学历 C 档"再按权重算才是可解释的 |
| 3 | **新增「综合评估」**（一面 + 二面合并出完整分析） | 你明确要求这一步 |
| 4 | **新增「谈薪」独立一步** | 你把谈薪和发 Offer 分开说的 |
| 5 | 看板 4 列 → **5 列**（待筛选 / 面试中 / 谈薪 / 待入职 / 已入职 + 已归档） | 你的流程就是 5 步；谈薪要能看见"有几个人在谈" |
| 6 | AI 只做三件：**画像、筛选判档、面试总结+综合** | 谈薪和 Offer 正文用模板生成，不值得花模型钱也不该让模型编薪资 |
| 7 | 面试评价、人工评分、1–5 星继续删 | 上一版已定，本版不变 |

**上一版继续有效的部分**：AI 结果自动出现不点按钮、引用逐字校验、禁用词、转写稿走粘贴（音频后续接）、复试做成第二轮、OpenAI 兼容 + 默认 DeepSeek、不新增一级导航、无模型必须能走完。

## 2. 硬约束（评审检查项）

1. **人只做决定，不写内容。** 任何要求 HR 手写超过一句话的地方，都算设计缺陷。
2. **模型不产出任何数字。** 分数、匹配度百分比、排名一律由服务端按画像权重计算；模型只输出"档位 + 原话"。
3. **分数必须可与原文对账。** 点开任何一个分数，能看到每个标签的档位和支撑原话。
4. **一个候选人一个主按钮**，按所在列自动变。
5. **不新增一级导航、不新增页面路由**；画像挂在岗位详情里，综合评估挂在候选人详情里。
6. **AI 必须有降级**：没配模型时，流程能走完，只是结论靠规则命中 + 一句话手填。

## 3. 流程：五列，五个决策点

### 3.1 看板

| 列 | 数据库落点 | 卡片显示 |
|---|---|---|
| **待筛选** | `stage='screening'` | 画像总分、硬性条件缺几条、第一句理由、停留天数 |
| **面试中** | `stage='interview'` | 第几轮（初试/复试）、下一场时间、本轮总结状态、综合评估状态 |
| **谈薪** | `stage='offer'` 且 `offers.status='negotiating'` | 预算区间、候选人期望、差额 |
| **待入职** | `stage='offer'` 且 `offers.status IN ('sent','accepted')` | Offer 薪资、到岗日、答复倒计时 |
| **已入职** | `stage='hired'` | 到岗日 |
| *已归档* | `status='rejected'` | 归档理由（AI 预填） |

> 谈薪和待入职**共用 `stage='offer'`**，靠 `offers.status` 分流——不用改 SQLite 的 CHECK 约束（改要重建表，`applications` 被 4 张表外键引用，风险大于收益）。看板查询里做一次左连接即可。

### 3.2 五个决策点

| # | 位置 | 人做什么 | 耗时 |
|---|---|---|---|
| 1 | 岗位详情 | 看一眼 AI 出的画像，改两笔，点「确认画像」 | 1 分钟（一个岗位一次） |
| 2 | 待筛选 | 看评分卡 → 「约面试」或「归档」 | 5–15 秒/人 |
| 3 | 面试中 | 定时间（日期 / 方式 / 面试官）→ 面完贴转写稿 → 看总结 → 「进复试 / 去谈薪 / 归档」 | 20 秒 + 30 秒 |
| 4 | 面试中（二面完） | 看 AI 综合评估 → 「去谈薪 / 归档」 | 30 秒 |
| 5 | 谈薪 / 待入职 | 记期望薪资与谈定薪资 → 「发 Offer」→ 人选答复后「接受 / 婉拒」 | 1–2 分钟 |

**除此之外没有任何必填项。**

### 3.3 每个动作之后系统干什么

| 动作 | 系统自动 |
|---|---|
| 新建岗位 | 立即后台生成画像（四指标 + 硬性条件 + 红线 + 加分项），页面顶部出现「画像待确认」 |
| 确认画像 | 画像锁定为 `approved`；此前已上传的简历按新画像重算 |
| 上传简历 | 解析字段 → 保存正文 → 按画像逐标签判档 → 算分 → 卡片出现评分与建议 |
| 点「约面试」 | `screening → interview`，写事件与审计 |
| 点「归档」 | `→ rejected`，理由取 AI 给的那条（可改） |
| 排面试 | 写面试记录、`application → interview`、后台生成提纲（基于画像缺口 + 简历疑点） |
| 贴转写稿 | 立即生成本轮总结（无按钮），完成后页面提示 |
| 点「进复试」 | 建 round=2 面试记录草稿，回到定时间 |
| 点「去谈薪」 | `interview → offer`，建 Offer 记录 `status='negotiating'`，预填预算区间与候选人期望 |
| 记录谈定 | 写 `final_salary`、`start_date`、`reply_deadline` |
| 点「发 Offer」 | `offers.status='sent'`，卡片自动从谈薪移到待入职，生成 Offer 正文（模板） |
| 人选接受 | `status='accepted'` |
| 点「入职」 | `stage='hired'`，写 `hired_at` |

### 3.4 归档规则（贯穿全程）

任何一个决策点都有次要按钮「归档」。归档时：

- 理由必须从既有 `REJECTION_REASONS` 枚举里选（AI 预填最贴的一条）；
- 写 `application_events.type='rejected'` + 审计；
- 保留全部历史（画像、评分、总结、综合评估），可「恢复」回原列——现有的恢复能力不改。

## 4. AI 三件（全部自动，无按钮）

### 4.0 统一约定

- 服务端调用，key 只存库、只回尾 4 位。
- **引用逐字校验**：`quote` 必须在原文里 `includes` 得到，否则整条丢弃并返回 `dropped` 数。
- **禁用词**：建议录用 / 建议淘汰 / 不予录用 / 推荐录用 等命中即丢；禁止推断年龄、婚育、籍贯、民族、健康。
- **模型不许输出数字**（分数、百分比、排名、"80% 匹配"）。
- 超时 45s；失败返回 `{ ok:false, reason }`，界面显示"AI 没生成，可重试"，**流程不阻塞**。
- 输入截断：简历 6000 字、JD 3000 字、转写稿 12000 字、画像 3000 字。
- 每次调用写 `ai_runs`（kind / subject / model / 耗时 / tokens / 状态），不存正文。
- 缓存：同一岗位画像 24 小时（除非 JD 变）；同一简历+同一画像的评分按哈希复用；同一转写稿按哈希复用。

### 4.1 岗位画像（建岗即生成）

这是筛选的**唯一依据**，结构完全按你们那份《岗位画像模板（标准版）》，但去掉画像编号、部门归类这类人工填表项。

**输出**：

```json
{
  "positioning": "负责 B 端客户从签约到续约的全流程服务",
  "hard_gates": [
    { "condition": "大专及以上学历", "how": "简历学历栏" },
    { "condition": "3 年及以上 B 端客户服务经验", "how": "简历工作经历" }
  ],
  "indicators": [
    {
      "name": "背景度",
      "weight": 25,
      "labels": [
        { "name": "学历背景", "weight": 10, "tiers": { "E": "初中及以下", "D": "高中/中专", "C": "大专（达标）", "B": "本科", "A": "硕士及以上" } },
        { "name": "经验背景", "weight": 15, "tiers": { "E": "无相关经验", "D": "1–2 年", "C": "3–4 年", "B": "4–6 年", "A": "6 年以上" } }
      ]
    },
    { "name": "心态度", "weight": 25, "labels": [] },
    { "name": "专业度", "weight": 30, "labels": [] },
    { "name": "组织度", "weight": 20, "labels": [] }
  ],
  "redlines": ["简历时间造假", "近两年跳槽 3 次以上"],
  "bonus": ["有同行业客户资源"],
  "not_wanted": ["通勤单程超 90 分钟"]
}
```

- 四指标 = **背景度 / 心态度 / 专业度 / 组织度**，权重总和必须 100（服务端校验，不合法就按平均 25 修正并标记）。
- 每指标 3–6 个标签，标签权重之和 = 该指标权重（同上校验）。
- 每标签必须有 5 档 E/D/C/B/A 的具体文字，**C 档 = 岗位达标线**。
- **合规转写**：原 JD 里若有性别、年龄、婚育、籍贯等字样，一律转成岗位客观要求（照你们模板里的做法），转写过的条目在界面上标一个小提示。
- 硬性条件 ≤6 条，红线 ≤3 条，加分项 ≤3 条，`not_wanted` ≤3 条。

**界面**：岗位详情顶部一张卡——定位一句、硬性条件列表、四指标权重条（可拖）、每指标标签可增删改档。左下「AI 重新生成」，右下「确认画像」。

**降级**：没配模型 → 用 JD 里的学历/年限/技能词生成一版粗糙画像（只填硬性条件 + 技能标签），人手动补，不挡流程。

### 4.2 简历筛选（上传即生成，按画像评分）

**模型输出**（只判档，不算分）：

```json
{
  "gates": [
    { "condition": "3 年及以上 B 端客户服务经验", "result": "pass | fail | unknown", "quote": "2019-2024 某公司 客户成功经理" }
  ],
  "labels": [
    { "indicator": "背景度", "label": "学历背景", "level": "B", "quote": "某大学 本科 2016-2020" },
    { "indicator": "专业度", "label": "客户成功方法论", "level": "unknown", "quote": null }
  ],
  "redlines": [],
  "top_reason": "5 年 B 端客户服务经验，覆盖岗位要求的 3 年线",
  "concerns": [{ "point": "无独立带团队经验", "quote": null }],
  "reject_reason": "经验不匹配"
}
```

**服务端算分**（确定性，可复算）：

```
系数        E=0  D=0.5  C=1.0  B=1.5  A=2.0
标签得分    labelScore = 标签权重 × 系数
总分        score = round( Σ(已判标签得分) / Σ(已判标签权重) × 100 )
待核实权重  unknown_weight = Σ(level='unknown' 的标签权重)
```

- `score = 100` 即"完全达标"（全部 C 档）；`150` 是"全 B"，`200` 是"全 A"。
- **未提及判 `unknown`，不计分也不当 0 分**，单独列成"待核实 x 分"，面试时优先问。
- 判定：`score < 80` → 不符；`80–120` → 符合；`> 120` → 超配（标"档位可能偏高，注意留人"）。
- **硬性条件缺任一条 → 直接不符**，卡片上红字写"缺：3 年 B 端经验"，分数照算仅供参考。
- **命中红线 → 直接不符**，与分数无关。
- 没有 `labels` 的样本（画像还没确认）→ 只走硬性条件 + 关键词，卡片标"画像待确认，分数不可用"。

**界面**：候选人卡片三行——总分 + 判定（符合/不符/超配）、最强的一条理由、缺的硬性条件（有则红字）。点开详情能看到每个标签的档位和原话，人可手工改档位 → 分数即时重算（改动记审计）。

**降级**：没配模型 → 只跑硬性条件（学历/年限/技能关键词），卡片显示"规则筛：技能命中 4/6 · 6 年 · 学历达标"，**不显示分数**（假分数比没分数更糟）。

### 4.3 面试总结 + 综合评估

**A. 本轮总结**（贴转写稿即生成）

输入：转写稿 + 本轮提纲 + 简历摘要 + 上一轮总结（复试时）。

```json
{
  "headline": "一轮 40 分钟，专业度过关，组织度只验证到流程层面。",
  "highlights": [{ "point": "主导过续约率从 71% 提到 89%", "quote": "我们把它从七十多提到快九十", "at": "12:40" }],
  "concerns": [{ "point": "被问跨部门冲突时只描述流程，没有具体案例", "quote": "一般就是先对齐目标", "at": "23:10" }],
  "unanswered": ["期望薪资未明确", "最快到岗时间未确认"],
  "indicators_checked": [{ "indicator": "专业度", "label": "客户成功方法论", "evidence": "strong | weak | none" }],
  "suggested": "advance | negotiate | reject",
  "reason": "专业度够，组织度证据不足，建议复试补追问。"
}
```

- 不产出分数、不产出评价正文、不产出推荐等级。
- `indicators_checked` 是给综合评估用的：**这一轮验证了画像里的哪些标签**，这样二面才知道补哪块。
- `suggested` 决定三个按钮里哪个高亮。
- 复试的提纲会优先问一面 `concerns` + `unanswered` + `evidence='none'` 的标签。

**B. 综合评估**（二面总结就绪后自动生成，一面后直接走谈薪的可跳过）

输入：两轮总结 + 画像 + 简历摘要。

```json
{
  "headline": "两轮一致：专业度扎实、能独立扛客户；组织度两次都没验证，薪资预期高于预算 2k。",
  "confirmed": [{ "point": "专业度：两轮都有独立扛客户的案例", "from": [1, 2] }],
  "conflicts": [{ "point": "一面称带过 3 人，二面说不清带人细节", "from": [1, 2] }],
  "uncovered": [{ "indicator": "组织度", "label": "跨部门推动", "why": "两轮都没问到具体案例" }],
  "recommendation": "proceed | reject",
  "reason": "建议进谈薪；组织度缺口在试用期验证。"
}
```

- `confirmed` 只允许引用两轮里真实出现过的话，`from` 必须是 `[1]`、`[2]` 或 `[1,2]`。
- `uncovered` 直接对应画像标签，一眼看出"这个人哪块还没验"。
- 界面：候选人详情里的「综合评估」卡，在二面总结下方；点「去谈薪」进下一列。

**降级**：没配模型 → 抽屉里只有转写稿 + 一个「一句话结论」输入框 + 去向按钮；综合评估卡显示两轮的手填结论并列，不做合并。**这条是底线，必须能走完。**

### 4.4 面试提纲（排面试时后台生成）

- 5 个问题，每个带「听什么」和一句追问；初试看简历疑点 + 画像弱项，复试看一面 `concerns` / `unanswered` / `evidence='none'`。
- 存 `interviews.plan_json`，在面试详情折叠展示，不打扰主流程。失败就空着。

### 4.5 不调模型的两处（故意）

| 位置 | 做法 |
|---|---|
| **谈薪** | 纯计算 + 模板句：预算 `salary_min–max`、候选人期望、差额、建议起谈点（`min(期望, 预算上限)` 与预算中值取小）、一句话话术（"我们预算上限 20k，先谈 20k + 三个月转正调薪"）。数据不全就只显示差额。 |
| **Offer 正文** | 模板渲染：岗位名、定薪、到岗日、答复期限、联系人。人可改后可发。 |

理由：薪资和承诺不该让模型编；模板已经够用，还便宜。

## 5. 数据模型

### 5.1 新表

```sql
-- 一张岗位一张画像，改 JD 可重生成并保留旧版
CREATE TABLE IF NOT EXISTS job_profiles (
  id            TEXT PRIMARY KEY,
  job_id        TEXT NOT NULL REFERENCES jobs(id) ON DELETE CASCADE,
  version       INTEGER NOT NULL DEFAULT 1,
  content_json  TEXT NOT NULL DEFAULT '{}',
  status        TEXT NOT NULL DEFAULT 'draft'
                CHECK (status IN ('draft','approved','failed')),
  generated_by  TEXT NOT NULL DEFAULT 'ai'
                CHECK (generated_by IN ('ai','manual','fallback')),
  approved_by   TEXT REFERENCES users(id),
  approved_at   TEXT,
  created_at    TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_job_profiles_job ON job_profiles(job_id, version DESC);

CREATE TABLE IF NOT EXISTS screening_reviews (
  id             TEXT PRIMARY KEY,
  application_id TEXT NOT NULL REFERENCES applications(id) ON DELETE CASCADE,
  profile_id     TEXT REFERENCES job_profiles(id),
  score          INTEGER,                 -- 服务端算的，模型不给
  verdict        TEXT
                 CHECK (verdict IS NULL OR verdict IN ('match','overqualified','mismatch')),
  unknown_weight INTEGER NOT NULL DEFAULT 0,
  missing_gates  TEXT NOT NULL DEFAULT '[]',
  redline_hit    TEXT NOT NULL DEFAULT '[]',
  detail_json    TEXT NOT NULL DEFAULT '{}',   -- gates / labels / top_reason / concerns
  decision       TEXT
                 CHECK (decision IS NULL OR decision IN ('advance','reject')),
  reason         TEXT,
  decided_by     TEXT REFERENCES users(id),
  decided_at     TEXT,
  model          TEXT,
  created_at     TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_screening_app ON screening_reviews(application_id, created_at DESC);

CREATE TABLE IF NOT EXISTS offers (
  id              TEXT PRIMARY KEY,
  application_id  TEXT NOT NULL UNIQUE REFERENCES applications(id) ON DELETE CASCADE,
  expected_salary INTEGER,         -- 候选人期望
  final_salary    INTEGER,         -- 谈定
  start_date      TEXT,
  reply_deadline  TEXT,
  status          TEXT NOT NULL DEFAULT 'negotiating'
                  CHECK (status IN ('negotiating','sent','accepted','declined')),
  decline_reason  TEXT,
  offer_letter    TEXT,            -- 模板渲染的正文，人可改
  created_by      TEXT REFERENCES users(id),
  created_at      TEXT NOT NULL,
  updated_at      TEXT NOT NULL,
  sent_at         TEXT,
  decided_at      TEXT
);

CREATE TABLE IF NOT EXISTS ai_runs (
  id          TEXT PRIMARY KEY,
  kind        TEXT NOT NULL,        -- profile | screening | questions | summary | composite | today
  subject_id  TEXT,
  input_hash  TEXT,
  model       TEXT,
  status      TEXT NOT NULL CHECK (status IN ('ok','failed','skipped')),
  error       TEXT,
  tokens_in   INTEGER,
  tokens_out  INTEGER,
  duration_ms INTEGER,
  actor_id    TEXT REFERENCES users(id),
  created_at  TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_ai_runs_created ON ai_runs(created_at DESC);
CREATE INDEX IF NOT EXISTS idx_ai_runs_hash ON ai_runs(input_hash, kind, created_at DESC);
```

## 11. 手测流程

### 第 0 步 · 准备

从项目目录运行 `npm run dev`，用测试账号登录 `http://127.0.0.1:5173`。用已有工作台时沿用现有账号和数据库，建一个带「实测」前缀的测试岗位。需要独立试用时，在终端为本次会话设置 `HIRELOOP_DATA_DIR` 指向新目录，再启动并在页面注册。

### 第 1 步 · 接真模型（3 分钟，必须先过）

用管理员账号打开「设置 → AI 模型」。官方 API 基础地址填 `https://api.deepseek.com`，模型 ID 填 `deepseek-flash`，对应版本为 **DeepSeek-V4.1-Flash-1017**。从设置页的「申请 API 密钥」进入 DeepSeek 开放平台。拿到密钥后填入页面，点「保存 AI 配置」，再点「测试连通性」。通过后会显示模型 ID 和延迟。[DeepSeek 官方 API 文档](https://api-docs.deepseek.com/zh-cn/)

- key **只填在页面上**（写库、只回尾 4 位），不进仓库、不写进 `.env` 提交、不贴到聊天里。
- 连接失败先修配置，**不要往下走**——后面每一步都依赖模型。

### 第 2 步 · 全流程一次跑完（30–40 分钟，重点）

用一个测试岗位、一份获准用于测试的真实简历和两段面试转写稿。验证真实数据前，确认可以将材料交给所配置的模型服务处理。

1. 新建岗位（标题 + 需求三五行）→ 等几秒 → 画像自动出现
   - 查：四指标权重加起来 100、每标签有 5 档文字、硬性条件 ≤6 条
   - 查：点任一标签，5 档是不是具体到能判（不是"优秀/良好"）
   - 查：原 JD 里若有不合规字样，是否被转成客观要求并标出
2. 点「确认画像」，再从职位详情打开「简历筛选」。把简历拖到上传区，或点「选择简历」。平台会建档并投递到当前职位，打开候选人的筛选结果
   - 查：支持 PDF、DOCX、TXT、MD，每次一份，最大 8 MB。重复上传会提示打开已有记录
   - 先读「AI 简历总结」。AI 从职业经历、主要职责、项目与成果中摘选关键原句，原简历入口可用来核对上下文。分析使用文件解析得到的文本，解析上限为 20,000 字符
   - 再按需展开「岗位画像评分（参考）」，核对当前已确认的画像版本与本次评分采用的版本。新草稿不参与评分，确认新版本后仍在待筛选的投递会重新分析
   - 已有旧记录可以点「重新筛选」生成总结。AI 暂不可用时可查看原简历后人工决定
   - 查：展开评分依据，核对有档位的标签是否都有原话支撑
   - 查：没提到的标签标了"待核实"，**没被算成 0 分**
   - 查：硬性条件缺一条时红字写明缺哪条
3. 试一次改档：把某个 D 改成 B → 分数应变高 → 时间线和审计里能看到改动
4. 看完总结后，由人点「推进初试」或归档。推进后再点「安排初试」。核对面试记录中 5 个提纲问题是否针对简历疑点和画像待核实项
5. 面完后打开面试记录，粘贴第一段转写稿，点「保存逐字稿并生成」。同一动作保存材料并启动总结
   - 查：headline 说清这一轮成没成
   - 查：核对亮点和顾虑的原话。原稿带时间戳时也核对时间点
   - 查：「未问到」里是不是真的没问
   - 查：总结是否指出这轮没有验证的要点
6. 点「进入复试」，系统创建第二轮草稿。点「安排复试」，完成后同样保存第二段转写稿。复试总结就绪后，系统自动生成两轮综合评估
   - 查：一致点/矛盾点分别标了来自第几轮
   - 查：「未覆盖」对得上画像里没验证的标签
7. 确认「进入谈薪」。录入期望月薪、最终月薪、到岗日期和答复期限并保存，核对预算差额。点「记录已发出」生成可复制的 Offer 文本。手测依次点「记录已接受」和「确认入职」，核对看板移入已入职列

**每步看三处**：状态对不对、时间线有没有、刷新后还在不在。

> 降级路径（没配模型也能走完）不进手测：这个能力由 `npm test` 里的 stub 模型用例覆盖（见 A16），每次跑测试都验一遍。手测只证明"真模型接上以后整条链路通"。

### 第 3 步 · 边界

| 场景 | 预期 |
|---|---|
| key 填错 | 「AI 没生成，可重试」，按钮仍可用 |
| 画像权重被人改成 90 | 保存时自动归一到 100，提示更新后的结果供复核 |
| 简历 30 页 | 解析按前 20000 字，提示已截断 |
| 转写稿 20 字 | 提示太短，要求 ≥200 字 |
| 转写稿 3 万字 | 提示已截断，按前 12000 字生成 |
| 同一转写稿贴两次 | 命中缓存，不重复计费（`ai_runs` 只有一条 ok） |
| 同一简历 + 同一画像重复打分 | 24 小时内命中缓存，不重复计费 |
| 模型偶尔胡说 | 引用校验丢弃伪造原话，响应带 `dropped`，总结不因一条假引用整块报错 |
| 没传转写稿就点去向 | 正向推进前需补一句结论，归档入口仍可用 |
| 一面完直接去谈薪（跳过复试） | 允许，综合评估跳过 |
| 谈薪中途归档 | 允许，`offers` 保留记录 |
| 直接调 AI 接口不带登录 | 401；用人经理调 → 403 |

### 第 4 步 · 设备与自动化

```bash
# 已有测试服务和网页模型配置时，设置 FLOW_BASE、FLOW_EMAIL、FLOW_PASSWORD 后执行
# 使用环境中已有 LLM_API_KEY 时，省略 FLOW_BASE，脚本会用隔离数据库
npm run flow

# 只跑规则与状态机，不调模型（CI 用，省钱）
npm run flow -- --no-llm

node scripts/measure.mjs --width 390 --width 768 --width 1440
node scripts/shot.mjs --only board --width 390
npm run check && npm test && npm run smoke
```

`scripts/flow.mjs` 覆盖的步骤（第 2 步的自动化版本，每步打印耗时和关键字段，任何一步不符合预期就非 0 退出）：

1. 注册/登入测试账号 → 建一个岗位 → 等画像生成后确认 → 断言四指标权重和为 100、每标签 5 档
2. 上传 `test-fixtures` 里的简历 → 等评分到 `ready` → 断言有分数、有 `unknown`、有原话引用
3. 约面试 → 断言 `stage='interview'`、提纲已生成
4. 贴一段转写稿 → 等总结 `ready` → 断言 `quote` 全部能在原文找到
5. 进复试 → 贴第二段 → 等总结 → 断言综合评估 `ready`
6. 去谈薪 → 断言差额算对 → 发 Offer → 断言卡片落到 `待入职` → 接受 → 入职
7. 打印各步耗时、总耗时和已配置工作台的累计 Token

> 手测只用来判断"生成的**内容**好不好"，`flow.mjs` 用来判断"链路通不通"。两件事分开，改代码后跑 `npm run flow` 就知道有没有退化，不用重新点一遍。

`npm test` 里必须有 stub 模型的用例覆盖：引用校验丢伪造引用、`unknown` 不计分、硬性缺项判定不符、无模型降级不崩。

## 12. 风险与未决

1. **分数会被当成结论。** 一出现数字，人就会只看数字。缓解：分数旁永远并排"缺哪条硬性条件"和"待核实权重"；评判卡默认展开两三个关键标签的档位；改档位留痕，防止人拿分数当挡箭牌。
2. **画像质量决定一切。** 画像的 5 档描述如果写成"优秀/良好"，分数就没有意义。缓解：提示词里强制"每档必须是一句可判定的客观描述"，验收 A1 要人眼过一遍；画像模板里带 1 个正例。
3. **AI 总结质量就是产品口碑。** 转写稿差（抢话、方言、专业词）会拖垮总结。缓解：提示词要求"听不清的不要编"，`quote` 校验兜底；面试页给"这段总结不准"一键反馈，收集坏样本。
4. **成本。** 自动生成 = 每次上传都可能调用。缓解：画像 24 小时缓存、评分按哈希缓存、转写稿按哈希缓存、输入截断；设置页可见累计 Token。
5. **降级能力不再靠手测守。** 手测直接接真模型跑全流程，没人会记得再去清空 key 试一遍——所以降级必须写成 stub 模型的自动化用例（A16），否则半年后就悄悄坏了。
6. **真模型手测的几个坑。** ① 一次全流程大约 6–8 次调用，留 5–10 元额度够跑十几轮；② 同一个输入两次结果可能不同，判定"对不对"看的是**引用能不能对上原文**，不是看它措辞；③ 遇到模型说"资料里没写"就标 `unknown`，这是正确行为，不要当 bug 报；④ 手测中发现不准的地方，当场点"这段总结不准"留样本。
7. **录音仍走粘贴。** 接口留 `transcript_source`，后续接 ASR 只多一步音频转文字，其余复用。本版不建音频表、不存音频。
8. **废弃旧规则要改测试。** `server/test/api.test.ts` 里「完成面试需要评分与反馈」的用例必须改写，并在 REVIEW.md 记录这是**有意的行为变更**，不是回归。
9. **5 列 vs 4 列。** 按你的流程做了 5 列；若嫌多，把「谈薪」并回「待入职」只需改看板分组条件，数据层不动。
10. **需求文档**等你走完第 11 节再写。
