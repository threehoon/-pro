# 协作开发规范

两人并行开发（框架 / AI 与画像）的落地规则。目标是：谁的改动归谁、冲突提前避、每一条进入 `main` 的代码都跑过检查。

## 1. 分支模型

```
main        稳定线：随时可演示、可部署（局域网 8790 跑的就是它的构建）
  └─ dev    集成线：两人合并的汇合点，允许短暂不可用
       ├─ feat/ai-interview-summary
       └─ fix/outbox-page-reset
```

- `main` 和 `dev` 都不直接 push，只通过 PR 合并（由分支保护兜底）。
- 功能分支一律从 `dev` 拉，PR 目标也是 `dev`；只有 `dev → main` 的 PR 由框架负责人发。
- 命名：`<类型>/<模块>-<一句话>`，类型取 `feat` / `fix` / `refactor` / `docs` / `chore`。
  例：`feat/ai-interview-summary`、`fix/outbox-page-reset`。
- 生命周期：一个分支不超过 3 天，合完立即删除。
- 提交信息：`类型(范围): 说明`，首行 ≤ 72 字符，正文写「为什么」。
  例：`feat(ai): 面试总结接入逐字稿`。

## 2. 日常命令流

```bash
git switch dev && git pull
git switch -c feat/ai-interview-summary

# 开发中，每完成一小块就跑一次
npm run check && npm test

git add -p && git commit
git push -u origin feat/ai-interview-summary
# 到 GitHub 开 PR → dev，等 CI 变绿 + 1 个 approve
```

合并之后：

```bash
git switch dev && git pull
git branch -d feat/ai-interview-summary
```

两人同时改动时先 `git pull --rebase` 再推；任何情况下都不要 `push -f` 到 `main` / `dev`。

## 3. 分支保护（GitHub Settings → Branches，配置一次长期生效）

`main`：

- Require a pull request before merging（至少 1 个 approve，勾选 Dismiss stale approvals）
- Require review from Code Owners
- Require status checks to pass，勾选 CI 里的「类型检查 / 测试 / 构建」
- Require branches to be up to date before merging
- 禁止 force push、禁止删除分支

`dev`：同上，但所需 approve 数量设为 0（自己的分支可以自己合），CI 必须绿。

## 5. 冲突高发区与约定

下面这些是两人都会碰的文件，改动前在群里说一句，并遵守追加规则：

1. `server/src/db/schema.sql`、`server/src/db/index.ts` 的 `ensureColumn` 块 —— 只允许「追加」新列或新索引，不改已有列的类型与语义；历史库靠幂等执行 + 增量加列升级。
2. `web/src/types.ts` —— 只追加类型，不改已有字段含义。
3. `web/src/lib/api.ts` —— 各自往文件末尾追加函数，不重排现有代码。
4. `web/src/styles/app.css` —— 新样式用独立前缀（`.ai-*` / `.outbox-*`），只在文件末尾追加区块。
5. `package.json` / `package-lock.json` —— 新增依赖单独开 PR，避免锁文件互相覆盖。

## 6. 契约先行

`docs/下一阶段开发文档.md` 已经把 AI 三件的接口、字段、状态机定好了（第 6 节接口表、5.2 加列清单、第 10 节验收）。据此分工：

- 框架侧先落地接口壳、数据列和前端占位状态；
- 同事只在约定范围内实现，不擅自改接口形状；确需调整时先更新该文档，并在 PR 描述里写明，由框架负责人合；
- 结果状态统一用 `pending / running / ready / failed`，前端复用同一套组件，不要为每块 AI 功能另造状态。

## 7. PR 与评审

PR 模板已就位（`.github/pull_request_template.md`）。评审只看四件事：

1. 契约有没有被悄悄改；
2. 权限有没有被绕过（服务端 `requireAdmin` 一类校验不能只靠前端隐藏）；
3. SQL 与外部输入是否都走参数绑定 / Zod 校验；
4. 失败路径有没有给用户可见的提示。

评审承诺 24 小时内回；不要攒到最后一起看。

## 8. 发布节奏

- `dev` 累积到「能演示」→ 发 `dev → main` 的 PR → 合并后打 tag（如 `v0.5`）。
- 只有合进 `main` 之后才重启 8790 的进程（它服务的是 `main` 的构建产物）。
- 发布前跑一遍：`npm run check && npm test && npm run build`。

## 9. 本地环境隔离

- 每人一份 `server/data/hireloop.db`（已在 `.gitignore`），不要互相拷库；跨库数据不一致会表现为「配置已保存 0 项」这类假故障。
- 端口分开：框架侧 8787 + 5173，AI 侧用 8791 和独立数据目录。
- LLM key 只放环境变量，不进仓库；`ai_runs` 里只记录 key 尾 4 位。
- 飞书凭据只在管理员的设置页可见；不要在测试里触发真实外发。
