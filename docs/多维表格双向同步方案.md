# 飞书多维表格双向同步方案（长连接模式）

> 状态：待确认。确认后按第 9 节分期实施。
> 目标版本：从 `dev` 的 `eb9c29b` 拉分支 `feat/bitable-sync`。

## 0. 目标与边界

**要做成的事**：系统是主数据，多维表格是"看得见、能写几列"的台账。

| 内容 | 方向 | 说明 |
| --- | --- | --- |
| 面试总结、AI 分析、逐字稿要点、指标核对 | 系统 → 表格 | 只读镜像，AI 生成后自动写入 |
| 投递阶段 | 系统 → 表格 | 只读镜像，展示用 |
| 面试结论、评分、补充反馈、本轮决定 | 表格 → 系统 | 白名单回写 |
| 投递的下一步、下次跟进、备注 | 表格 → 系统 | 白名单回写 |
| 姓名、手机、邮箱、职位、面试时间、负责人 | 系统 → 表格 | 只读，表格改动被拒绝并记差异 |
| 淘汰 / 归档 | — | **不允许在表格里操作**，必须回系统点 |

**明确不做**：表格当主库、任意列自由编辑、表格里删除行就真删系统数据、把简历附件推进飞书云空间。

## 1. 整体架构

```
业务事件（阶段变更 / 总结生成 / 结论修改 / 入职）
        │
        ▼
 bitable_sync_queue ──► 出站 worker（串行、批量 ≤500、失败退避重试）
        │                        │
        │                        ▼
        │                  飞书多维表格（Base）
        │                        │
        │            记录变更事件 drive.file.bitable_record_changed_v1
        │                        │  （WebSocket 长连接，无需公网）
        │                        ▼
        │                 事件入站处理器（3 秒内 ack，只落库）
        │                        │
        │                        ▼
        └──────────── 入站 worker（去重 → 白名单 → 状态机 → 写库 + 时间线 + 通知）
                                 │
                                 ▼
                        反向回写一次，让表格显示系统最终值
```

三条原则：

1. **两个 worker 都串行**：飞书同一个 table 不支持并发写（会报 `1254291 Write conflict`），所以出站按表排队，一次只发一个请求。
2. **入站优先 ack**：长连接要求在 3 秒内处理完，否则飞书会超时重推。handler 只做"验 + 落盘 + 返回"，重活交给队列。
3. **幂等到底**：`event_id` 唯一入库；字段用"值哈希"判断是不是我们自己写的。

## 2. 飞书侧前置（需要你在后台点，代码无法代替）

1. **应用权限**：给现有自建应用开通 `bitable:app`（或 `drive:drive`），并且**应用身份与用户身份都要开**——官方文档明确要求双身份权限才能订阅"多维表格记录变更"事件。
2. **事件订阅方式**：开发者后台 → 事件与回调 → 订阅方式选 **长连接**。
3. **订阅事件**：添加 `drive.file.bitable_record_changed_v1`。
4. **订阅具体文件**：该事件的前置条件是要调用「订阅云文档事件」接口（`POST /open-apis/drive/v1/files/{app_token}/subscribe?file_type=bitable`）。我会把它做成设置页里的一个按钮，失败时给出明确原因（通常是应用没被加进 Base）。
5. **Base 授权**：把应用加成 Base 的协作者；如果 Base 开了高级权限，需要建一个包含该应用的群并授予读写。
6. **发布版本**：权限变更后要发布新版本才生效。

> 已知坑：这条事件在部分环境比较挑剔（需要双身份权限 + 先订阅文件），所以第 6 节保留了**低频兜底对账**。它不是主通道，但能在事件丢了的时候把数据对回来。

## 3. 数据模型（新增 3 张表）

```sql
-- 同步配置：Base 与各表 ID、字段缓存、开关
CREATE TABLE IF NOT EXISTS bitable_config (
  id             TEXT PRIMARY KEY,          -- 固定 'default'
  app_token      TEXT,                      -- Base token（base 链接里的 basxxxx）
  interviews_table_id   TEXT,
  applications_table_id TEXT,
  fields_json    TEXT NOT NULL DEFAULT '{}',-- 字段名 → field_id 缓存（联调时探测）
  enabled        INTEGER NOT NULL DEFAULT 0,
  fallback_minutes INTEGER NOT NULL DEFAULT 0, -- 0 = 不开启兜底对账
  last_event_at  TEXT,
  last_reconcile_at TEXT,
  updated_by     TEXT,
  updated_at     TEXT NOT NULL
);

-- 实体 ↔ 记录的映射
CREATE TABLE IF NOT EXISTS bitable_records (
  entity_type    TEXT NOT NULL,             -- 'interview' | 'application'
  entity_id      TEXT NOT NULL,
  table_id       TEXT NOT NULL,
  record_id      TEXT NOT NULL,
  pushed_hash    TEXT,                      -- 系统最后推给表格的业务值哈希
  pushed_at      TEXT,
  pulled_hash    TEXT,                      -- 表格最后回写的值哈希
  pulled_at      TEXT,
  state          TEXT NOT NULL DEFAULT 'synced', -- synced | pending | error | orphan
  last_error     TEXT,
  PRIMARY KEY (entity_type, entity_id)
);

-- 出站队列
CREATE TABLE IF NOT EXISTS bitable_sync_queue (
  id            TEXT PRIMARY KEY,
  entity_type   TEXT NOT NULL,
  entity_id     TEXT NOT NULL,
  op            TEXT NOT NULL,              -- 'upsert' | 'delete'
  state         TEXT NOT NULL DEFAULT 'pending', -- pending | sending | sent | failed
  attempts      INTEGER NOT NULL DEFAULT 0,
  next_attempt_at TEXT,
  error         TEXT,
  created_at    TEXT NOT NULL,
  updated_at    TEXT NOT NULL
);

-- 入站事件去重
CREATE TABLE IF NOT EXISTS bitable_events (
  event_id      TEXT PRIMARY KEY,
  table_id      TEXT,
  record_id     TEXT,
  action        TEXT,
  operator_open_id TEXT,
  payload_json  TEXT NOT NULL,
  state         TEXT NOT NULL DEFAULT 'pending', -- pending | applied | ignored | conflict
  note          TEXT,
  received_at   TEXT NOT NULL,
  applied_at    TEXT
);
```

字段用 `ensureColumn` 加在既有表上（下一步要写的三列）：

```ts
ensureColumn(conn, 'applications', 'next_step', 'TEXT');
ensureColumn(conn, 'applications', 'next_follow_up_at', 'TEXT');
ensureColumn(conn, 'applications', 'bitable_note', 'TEXT');
```

## 5. 出站（系统 → 表格）

- **触发点**（都挂 `afterCommit`，不阻塞业务请求）：阶段变更、面试总结生成完成、面试结论/评分/反馈修改、面试取消、投递归档/恢复、入职。
- **worker 逻辑**：取 `state='pending'` 且到了重试时间的记录，按 `table_id` 分组，串行处理；单条 upsert 用 `records/batch_create`（无 `record_id`）或 `records/batch_update`（有 `record_id`），单次 ≤500 条（我们单批最多 20 条，留足余量）。
- **写回后**：把 `record_id`、业务值哈希、`pushed_at` 写进 `bitable_records`，队列置 `sent`。
- **失败**：记 `error`，指数退避（10s / 30s / 2min / 10min / 30min，5 次后置 `failed`），管理页可手动重试；`1254290 TooManyRequest` 与 `1254291 Write conflict` 单独识别，退避更长。
- **量级**：单表 20 000 行上限。我们只镜像"未归档且近 24 个月"的投递与全部未完成面试；归档数据留在系统里查。

## 6. 入站（表格 → 系统）

**连接**：`@larksuiteoapi/node-sdk` ≥ 1.24.0 的 `WSClient`，在 `server/src/index.ts` 启动时建连；未配置飞书则跳过；设置页改了密钥就重建连接。长连接只在建连时鉴权，事件是明文，不需要我们再做解密验签。

**handler（必须在 3 秒内返回）**：

1. 只处理 `event_type === 'drive.file.bitable_record_changed_v1'` 且 `table_id` 属于我们这两张表的事件；
2. `event_id` 已存在 → 直接返回（重复投递丢弃）；
3. 把 `event` 原样写入 `bitable_events`（`state='pending'`）；
4. 返回，不在这里做业务写入。

**入站 worker（异步）**：

1. 取 `pending` 事件，按 `record_id` 找到 `bitable_records` 对应的实体；找不到 → `state='ignored'`（不是我们推上去的行，比如人手工新建的）；
2. **回环抑制**：`operator_id.open_id` 属于本应用写入的，或变更值与 `pushed_hash` 一致 → `ignored`；
3. **白名单校验**：只取允许回写的列；出现非白名单列的变化 → `state='conflict'`，写差异日志，**拒绝整条**并反向回写让表格显示系统值；
4. **状态机校验**：阶段只能相邻推进、决定/评分枚举必须合法；非法值 → 拒绝 + 反向回写；
5. **写系统**：调用既有服务函数（不是裸 UPDATE），保证 `application_events` 时间线、飞书通知、审计都照常触发；
6. 更新 `bitable_records.pulled_hash/pulled_at`，事件置 `applied`；
7. **反向回写**：把系统最终值再推到表格那一行（覆盖被拒绝的非法输入），避免"看着改了其实没生效"。

**兜底对账**（`bitable_config.fallback_minutes > 0` 时启用，默认关闭，建议 10 分钟）：

- 按 `last_modified_time` 或全量分页拉记录（500/页），只比对白名单列与 `pushed_hash`；
- 差异交给**同一个** `applyBitableChange` 函数处理 → 与事件通道共用全部校验与幂等逻辑；
- 目的：事件丢了（权限变更、连接抖动、订阅被取消）也能对回来。

## 7. 冲突与审计

| 场景 | 处理 |
| --- | --- |
| 表格改了只读列 | 拒绝 + 反向回写 + 差异日志（`bitable_events.state='conflict'`） |
| 表格改了白名单列，系统同时改了同一列 | 后写者胜，但保留审计；界面上「同步状态」列显示"冲突" |
| 表格删了行 | 系统不删，`bitable_records.state='orphan'`，管理页列出 |
| 系统删/归档了实体 | 表格行保留并打标，队列发 `op='delete'` 时只清 `record_id`，不删行 |
| 事件重复投递 | `event_id` 主键去重 |
| 事件乱序 | 先比对 `pushed_hash`，与系统当前值一致才覆盖，否则走冲突 |

所有写入都写现有 `audit_log`：`bitable.push`、`bitable.pull`、`bitable.reject`、`bitable.subscribe`。

## 8. 安全

- `app_id` / `app_secret` 复用现有 integrations 存储，界面只回尾 4 位。
- `app_token` / `table_id` 在设置页填写并做格式校验，只允许字母数字。
- 长连接建连即鉴权，不接受外部 HTTP 推入，**不需要**再开放任何入站端口或做 IP 白名单。
- AI 总结会带候选人原话，属敏感信息：Base 的人可见范围要单独收，不能放进全员可见的知识库；实施时在设置页给出这句提醒。

## 10. 风险

1. **事件通道有已知脆弱点**：需要双身份权限、需要先订阅具体 Base、部分环境报错不明确。→ 保留兜底对账 + 设置页"自检"按钮（检查权限、订阅、表结构）。
2. **同一个 table 不能并发写**：→ 单表串行队列，绝不并发。
3. **单表 20 000 行上限**：→ 只镜像活跃数据，归档留系统。
4. **隐私面扩大**：总结与原话进表格后，可见范围从"系统角色"变成"Base 协作者"。→ 默认不推逐字稿全文，只推摘要与引用片段；Base 权限单独交代。
5. **长连接是新依赖**：SDK 版本要 ≥1.24.0，进程重启会断一下（自动重连）；`npm run dev` 的 `--watch` 会频繁重连，开发时需要能忍。
6. **字段被人改名/改类型**：→ 字段以 `user_id_type` 无关的 `field_id` 为准并缓存，启动自检发现不匹配直接报错，不静默丢数据。
